# Portfolio Deep Dive: Advanced Automation & Anti-Detection

This document contains in-depth analysis of the core mechanisms driving the advanced features across the portfolio repositories. These concepts can be ported directly to **Tokiyo Edge Automation**.

## 1. Content Generation & Intelligence Layer (`linkedin-as-a-service`)
**Core File:** `comment_service.py` & `system_comment.txt`

The AI engine does not just ask for "a comment". It enforces a strict, structured JSON schema to guarantee three distinct psychological strategies for engagement:
- **Insightful:** Forces the AI to add a complementary data point or real-world application, proving deep reading.
- **Contrarian:** Respectfully pushes back on a premise or introduces an edge case, driving high engagement via debate.
- **Supportive:** Validates the core point using a highly specific, first-person anecdote.

**Anti-Bot Guardrails:** 
The system enforces a negative blocklist in the prompt (banning words like "synergy", "delve", "game-changer") and strictly forbids repetitive openers like "Great post!". This ensures the edge devices do not sound like typical ChatGPT bots.

## 2. Anti-Detection & Fleet Stability (`founders-product`)
**Core Files:** `jitter.py` & `proxy_manager.py`

### The Jitter Engine (Gaussian Pacing)
Instead of hardcoding a `sleep(30)`, the system calculates execution delays using a **Gaussian distribution**. 
- Formula: `offset = (index * MU_OFFSET) + N(0, SIGMA)`
- This creates an organic spread of engagement across a time window. If Tokiyo dispatches 10 edge devices to like a post, they won't hit it exactly 30 seconds apart. Some will be 22s, others 45s, creating a mathematically human pattern.

### Geo-Preserving Proxy Rotation
The `ResidentialProxyManager` manages sticky sessions by dynamically injecting session IDs into proxy credentials (e.g., `-session-uuid`). 
- **The Genius Detail:** If a residential proxy dies (e.g., the homeowner turns off their router), the rotation engine extracts the exact latitude/longitude or city of the dead proxy. It then uses the **Haversine formula** to find the closest available proxy node and reconnects there. 
- This prevents triggering "Impossible Travel" algorithms on Instagram/LinkedIn.

## 3. MobileDeviceNetworkConnection (`adbwatch`)
**Core File:** `adbwatch.py`

A lightweight, dependency-free Python daemon designed to keep physical Android devices connected wirelessly.
- **mDNS Fallback:** Wireless debugging ports on Android often cycle dynamically when the screen sleeps. `adbwatch` constantly polls the device state. If it goes offline, it uses `adb mdns services` to auto-discover the new port and reconnects automatically.
- **Self-Healing Loop:** It maintains a JSON state file (`state.json`) and gracefully recovers without manual intervention. Deploying this on the Mac Mini hosting the Tokiyo devices ensures the Edge fleet never drops offline.

## 4. Advanced UI Automation & Self-Healing (`instagram-ai-automation-tmp`)
**Core File:** `appium_posting_service.py`

This repository solves the exact problem Tokiyo faces (UI unreliability) using a robust **3-Strategy Fallback System** for locating UI elements on the edge device:

1. **Strategy 1 (Appium Native):** Tries standard XPath/ID locators.
2. **Strategy 2 (XML Dump + Math):** If standard locators fail, it dumps the entire raw XML of the screen (`driver.page_source`), parses it with Python's `xml.etree`, finds the node containing the target `content-desc`, calculates the exact center pixel `((x1+x2)/2, (y1+y2)/2)`, and executes a raw `adb shell input tap`.
3. **Strategy 3 (Hard Coordinates):** If all else fails, it relies on fallback coordinates calibrated for the specific device resolution.

**Contextual Recovery:**
It also includes logic to detect if an uploaded video was muted by Instagram and automatically navigates the UI to apply a trending audio track, ensuring the post doesn't fail silently.
